## 1. 设计目标

本设计文档说明个人本地待办应用 MVP 的技术结构、组件边界、数据流和验证方式，用于指导后续实现。

设计必须满足以下目标：

- 完全支持需求规格中的 FR-01 至 FR-12。
- 数据只保存在当前浏览器中，不需要后端。
- 不需要安装依赖，不引入框架和构建工具。
- 页面可以直接作为静态站点运行。
- 主要逻辑边界清晰，便于测试和以后扩展。
- 第一版代码保持精简，不实现需求之外的通用功能。

## 2. 设计约束

- 使用 HTML、CSS 和原生 JavaScript。
- 使用浏览器 `localStorage` 保存任务。
- 使用单页结构，不引入前端路由。
- 不引入组件库、状态管理库、测试框架或打包器。
- 用户输入只能作为纯文本渲染，不能作为 HTML 执行。
- 所有数据属于当前浏览器的当前站点来源，不提供跨设备同步。
- 第一版必须适配常见桌面和手机宽度。

## 3. 总体架构

应用采用简单的三层结构：

1. 表现层：HTML 负责页面结构，CSS 负责布局和状态样式。
2. 应用层：JavaScript 负责应用状态、事件处理、数据转换和界面渲染。
3. 存储层：JavaScript 中的本地存储适配逻辑负责读写 `localStorage`。

```text
用户操作
   |
   v
DOM 事件
   |
   v
应用状态更新
   |
   +--> 本地存储保存
   |
   v
重新渲染受影响的界面
```

应用不拆分后端服务，不拆分数据库，也不建立网络请求层。所有数据流都在当前页面内完成。

## 4. 文件结构

第一版采用三个运行时文件：

```text
/
├── index.html
├── styles.css
└── app.js
```

职责划分：

| 文件 | 职责 |
| --- | --- |
| `index.html` | 页面语义结构、输入区域、筛选区域、列表挂载点和状态提示区域 |
| `styles.css` | 基础视觉、布局、响应式、完成状态、空状态和焦点样式 |
| `app.js` | 应用状态、数据校验、任务操作、存储读写、渲染和事件处理 |

`app.js` 内部按职责分区，但不为了单页 MVP 建立额外模块或复杂抽象。

建议的逻辑顺序：

1. 常量和 DOM 引用
2. 存储适配
3. 数据校验和转换
4. 状态操作
5. 渲染函数
6. 事件处理
7. 初始化

## 5. 应用状态

应用运行时使用一个内存状态对象：

```text
appState
├── tasks: Task[]
├── filter: "all" | "active" | "completed"
├── editingTaskId: string | null
├── storageAvailable: boolean
└── storageNotice: string | null
```

状态说明：

| 字段 | 是否持久化 | 说明 |
| --- | --- | --- |
| `tasks` | 是 | 用户当前的全部任务 |
| `filter` | 否 | 当前筛选条件，刷新后恢复为 `all` |
| `editingTaskId` | 否 | 当前正在编辑的任务标识 |
| `storageAvailable` | 否 | 当前环境是否可以使用本地存储 |
| `storageNotice` | 否 | 需要向用户显示的存储异常提示 |

`filter` 和 `editingTaskId` 属于界面状态，不写入本地存储。`tasks` 是唯一需要跨页面刷新保存的数据。

## 6. 数据模型

### 6.1 持久化结构

`localStorage` 使用固定键名：

```text
personal-todo.mvp.v1
```

键名保持不变，避免升级时丢失用户现有数据；实际数据结构版本以负载中的 `version` 为准。

存储值使用一个带版本号的 JSON 对象。截止时间扩展使用版本 `2`：

```json
{
  "version": 2,
  "tasks": [
    {
      "id": "task-id",
      "title": "完成第一版",
      "completed": false,
      "createdAt": "2026-09-30T10:00:00.000Z",
      "updatedAt": "2026-09-30T10:00:00.000Z",
      "dueAt": "2026-10-01T10:00:00.000Z"
    }
  ]
}
```

### 6.2 任务对象

任务对象必须包含以下字段：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | string | 非空且唯一 |
| `title` | string | 去除首尾空格后非空 |
| `completed` | boolean | `true` 表示已完成 |
| `createdAt` | string | 有效的 ISO 8601 时间字符串 |
| `updatedAt` | string | 有效的 ISO 8601 时间字符串 |
| `dueAt` | string 或 null | `null` 表示未设置；非空时必须是有效 ISO 8601 字符串 |

任务创建顺序和显示顺序分开处理。任务数组保存原始数据，渲染时统一按 `createdAt` 倒序排列，最新任务显示在最上方。

截止时间不参与默认排序。逾期状态由 `dueAt`、`completed` 和当前时间计算，不单独持久化。

### 6.3 标识生成

优先使用浏览器提供的 `crypto.randomUUID()`。

如果运行环境不支持，则使用当前时间戳和随机数组合生成一个在当前任务集合中不重复的字符串。第一版不需要引入 UUID 依赖。

## 7. 存储设计

### 7.1 读取

页面初始化时执行以下步骤：

1. 检查 `window.localStorage` 是否可访问。
2. 读取固定键名对应的字符串。
3. 如果字符串不存在，返回空的版本 2 数据结构。
4. 如果字符串可以被解析，则验证版本号和任务数组结构。
5. 如果版本为 `1`，将每个任务补充 `dueAt: null` 后迁移为版本 `2`。
6. 如果解析或验证失败，返回空任务列表并设置存储提示。

读取和验证必须是纯数据操作，不直接操作页面元素。

### 7.2 写入

每次任务数据发生变化后执行写入：

- 添加任务后
- 修改任务标题或截止时间后
- 切换完成状态后
- 删除任务后

写入失败时，内存中的任务仍然保留，当前页面继续可用，同时显示“数据无法永久保存”的提示。

### 7.3 数据校验

读取后的数据必须经过统一校验：

- 顶层对象必须包含正确的 `version`。
- `tasks` 必须是数组。
- 每个任务必须具有合法字段和正确类型。
- `title` 去除空格后不能为空。
- `id` 必须是字符串且不能重复。
- `createdAt` 和 `updatedAt` 必须是可解析的时间字符串。
- `dueAt` 必须是 `null` 或有效的时间字符串。
- 版本 1 数据按照迁移规则转换为版本 2，而不是判定为损坏。

第一版采用整体校验策略。如果顶层结构损坏，则回退到空列表，而不是尝试保留部分不可靠数据。

### 7.4 存储不可用

如果浏览器禁用本地存储、访问抛出异常或保存配额不足：

- 应用继续使用内存状态。
- 任务操作在当前会话内仍然有效。
- 页面显示明确的非阻断提示。
- 不通过弹窗中断用户操作。
- 不清除原始存储内容。

## 8. 界面组件

应用由以下逻辑组件组成：

### 8.1 AppShell

负责页面标题、主要内容容器和全局提示区域。

### 8.2 AddTaskForm

包含：

- 带明确标签的任务输入框
- 带明确标签的可选截止时间输入项
- 添加按钮
- 输入错误提示区域

行为要求：

- 提交时去除输入首尾空格。
- 截止时间为空时创建无期限任务。
- 非空截止时间转换为 ISO 8601 后保存。
- 空输入不产生任务。
- 提交成功后清空任务标题和截止时间并重新聚焦任务输入框。
- 支持 Enter 和按钮两种提交方式。

### 8.3 FilterBar

包含三个互斥选项：

- 全部
- 未完成
- 已完成

当前选项必须有可见选中状态，并提供可被辅助技术识别的状态。

### 8.4 TaskList

负责根据 `filter` 显示任务或空状态。

空状态分为两种情况：

- 完全没有任务：提示先添加一个任务。
- 当前筛选没有结果：提示该筛选条件下暂无任务。

### 8.5 TaskItem

单个任务项包含：

- 完成复选框
- 任务标题
- 截止时间文本和逾期状态
- 编辑按钮
- 删除按钮

编辑状态下，任务标题替换为文本输入框，截止时间替换为本地日期时间输入框，并显示保存和取消操作。

截止时间显示规则：

- 未设置时不显示期限区域。
- 已设置时显示本地化的年月日、小时和分钟。
- 未完成且 `dueAt` 早于当前时间时显示“已逾期”。
- 已完成时始终不显示逾期。

### 8.6 StatusSummary

显示未完成任务数量，例如：

```text
还有 3 项未完成
```

数量必须随任务状态变化即时更新。

### 8.7 StorageNotice

当本地存储不可用、读取失败或保存失败时显示提示。正常状态下不占用视觉空间。

## 9. 页面布局

页面采用居中的单列布局：

1. 标题和简短说明
2. 添加任务表单
3. 筛选栏
4. 任务列表或空状态
5. 剩余任务统计
6. 存储异常提示

桌面端：

- 主内容区设置合理最大宽度。
- 添加表单使用任务标题、截止时间和按钮的横向布局。
- 任务项使用复选框、内容区和操作区的三列布局。
- 长标题占用剩余空间并正常换行。

手机端：

- 主内容区保留安全边距。
- 任务标题、截止时间和添加按钮按纵向排列。
- 任务操作区保持可点击尺寸。
- 任务标题、截止时间、复选框和操作按钮不得相互遮挡。

视觉上使用安静的工具型风格，使用系统字体和有限的中性色。主操作使用一个强调色，完成状态、错误状态和普通状态必须有足够对比度。

## 10. 渲染策略

第一版使用简单、可预测的完整列表重渲染策略。

任务数据变化后：

1. 更新内存中的 `tasks`。
2. 写入本地存储。
3. 根据状态重新计算当前筛选结果。
4. 更新列表、剩余数量和空状态。

筛选条件变化和编辑状态变化只触发重新渲染，不触发存储写入。

渲染时使用 DOM 文本节点或 `textContent` 写入任务标题，禁止将用户输入拼接到 `innerHTML`。

列表事件使用事件委托，由 `TaskList` 统一处理完成、编辑、保存、取消和删除操作，避免为每次重渲染绑定无法追踪的重复监听器。

逾期样式由当前时间计算。页面打开后不启动定时器；刷新、筛选或任意数据变化触发重新渲染时重新计算逾期状态。

## 11. 关键流程

### 11.1 初始化

```text
页面加载
  -> 检查存储能力
  -> 读取并校验存储数据
  -> 建立 appState
  -> 绑定事件
  -> 渲染页面
```

初始化失败时必须进入可用状态。任务列表可以为空，但页面不能因为存储异常而停止工作。

### 11.2 添加任务

```text
提交输入
  -> 读取并 trim 标题
  -> 读取可选截止时间
  -> 转换为 ISO 8601 或 null
  -> 标题为空则显示验证提示
  -> 创建完整任务对象
  -> 加入 tasks 顶部或按时间排序
  -> 保存
  -> 重新渲染
  -> 清空任务输入和截止时间输入
  -> 聚焦任务输入框
```

### 11.3 切换完成状态

```text
点击复选框
  -> 找到目标任务
  -> 切换 completed
  -> 更新 updatedAt
  -> 保存
  -> 重新渲染
```

如果当前筛选为“未完成”，刚完成的任务会从列表中移除。如果当前筛选为“已完成”，取消完成后任务会从列表中移除。

### 11.4 编辑任务

```text
点击编辑
  -> 设置 editingTaskId
  -> 将该任务切换为输入状态
  -> 用户保存或取消
```

保存时：

```text
读取编辑值
  -> trim
  -> 空值提示并保持编辑状态
  -> 读取并转换截止时间
  -> 更新 title、dueAt 和 updatedAt
  -> 保存
  -> 清除 editingTaskId
  -> 重新渲染
```

取消时恢复原任务内容，不修改存储。

### 11.5 删除任务

```text
点击删除
  -> window.confirm 确认
  -> 用户确认后删除任务
  -> 保存
  -> 重新渲染
```

用户取消确认时不修改任务数据。

### 11.6 筛选任务

```text
点击筛选选项
  -> 更新 filter
  -> 重新计算可见任务
  -> 重新渲染列表和空状态
```

筛选不修改任务，不写入本地存储。

## 12. 异常处理

| 场景 | 处理方式 |
| --- | --- |
| 空标题 | 阻断提交，显示输入提示，保留输入焦点 |
| 截止时间为空 | 合法，保存为 `null` |
| 截止时间无法转换 | 阻断保存并显示输入提示 |
| 版本 1 数据 | 自动迁移为版本 2，原任务保留且 `dueAt` 为 `null` |
| 版本 2 的 `dueAt` 非法 | 按损坏数据整体回退 |
| 标题过长 | 正常保存，界面负责换行 |
| 存储不可用 | 切换为内存模式，显示非阻断提示 |
| 存储数据无法解析 | 使用空列表，显示提示，不崩溃 |
| 顶层结构版本不匹配 | 使用空列表并提示数据无法读取 |
| 保存失败 | 保留内存数据，提示无法永久保存 |
| 删除目标不存在 | 忽略该操作，重新渲染当前有效状态 |
| 编辑目标不存在 | 退出编辑状态，重新渲染当前有效状态 |
| 重复点击提交 | 提交过程中使用同步状态更新，避免重复任务 |
| 数字或特殊字符标题 | 作为普通纯文本处理 |

## 13. 无障碍设计

- 使用语义化 `header`、`main`、`form`、`button`、`ul` 和 `li`。
- 输入框必须有关联的 `label`。
- 截止时间输入项必须有关联的 `label`。
- 添加按钮、编辑按钮和删除按钮必须有可理解的可访问名称。
- 复选框使用原生元素，保证键盘可操作。
- 当前筛选状态不能只依赖颜色，必须有文字或 `aria-pressed` 等状态。
- 剩余数量和存储提示使用适当的 `aria-live` 区域。
- 所有交互元素必须有清晰的键盘焦点样式。
- 保持合理的文本和背景对比度。

## 14. 响应式设计

目标宽度范围：

- 最小支持宽度：320px
- 常见手机宽度：375px 至 430px
- 常见桌面宽度：1024px 及以上

响应式规则：

- 使用流式宽度和 `max-width`，不依赖固定页面宽度。
- 任务标题允许换行并使用 `overflow-wrap` 处理长单词或连续字符。
- 操作按钮保持稳定尺寸，不能被标题挤压。
- 在窄屏下允许添加区域从横向排列切换为纵向排列。
- 页面主要内容不得产生不必要的横向滚动。

## 15. 安全与隐私

- 所有任务内容只作为纯文本处理。
- 不将用户输入直接插入 HTML。
- 不发送网络请求。
- 不收集分析数据。
- 不写入浏览器外的位置。
- 清除站点数据后，本地任务会一并消失，这是当前设计接受的限制。

### 16.1 数据层验证

重点验证：

- 空存储读取
- 正确结构读取
- JSON 解析失败
- 版本号不匹配
- 版本 1 到版本 2 的迁移
- 任务字段类型错误

- 重复标识处理
- 添加、修改、完成和删除后的写入
- 存储写入失败时的内存回退

### 16.2 交互验证

重点验证：

- Enter 添加
- 按钮添加
- 空内容添加
- 只有空格的内容添加
- 添加带截止时间的任务
- 添加不带截止时间的任务
- 编辑和清除截止时间
- 逾期状态和已完成任务的非逾期状态
- 完成和取消完成
- 编辑保存和取消
- 编辑为空时不能保存
- 删除确认和取消
- 三类筛选切换
- 空状态和无筛选结果状态
- 剩余数量更新

### 16.3 浏览器验证

至少检查：

- 页面加载无阻断错误
- 刷新后任务保持一致
- 本地存储损坏后页面仍可用
- 320px 手机宽度下无重叠和横向溢出
- 桌面宽度下排版正常
- 键盘可以完成主要操作

第一版不强制引入自动化测试框架。为了保留后续自动化空间，数据校验和任务转换逻辑应保持为清晰、可独立调用的函数。

## 18. 设计取舍

选择原生静态方案的原因：

- MVP 只有单页面和少量交互。
- 数据完全属于当前浏览器，不需要网络层。
- 无依赖方案更容易直接运行和排查问题。
- 当前功能不需要组件框架或状态管理库。

有意保持简单的地方：

- 使用完整列表重渲染，不建立虚拟 DOM。
- 使用 `window.confirm` 删除确认，不实现自定义弹窗。
- 使用 `localStorage`，不引入 IndexedDB。
- 只持久化任务，不持久化筛选和编辑状态。
- 截止时间只保存 `dueAt`，不保存提醒状态或完成时间。
- 逾期状态按当前时间派生，不写入存储。
- 不建立通用存储接口，只保留一个小的存储适配区域。

这些取舍符合当前规模。只有当数据量、协作能力或同步需求真正出现时，才考虑引入更复杂的存储和组件结构。

## 19. 后续扩展方向

以下内容不属于第一版，但当前结构应允许未来扩展：

- 为任务增加提醒、优先级和标签字段。
- 将 `localStorage` 适配替换为后端 API。
- 增加账号和云同步。
- 增加搜索、排序和拖拽。
- 增加自动化测试和持续集成。

扩展时继续遵循一个原则：先修改需求规格和设计文档，再修改实现。

## 20. 设计完成标准

本设计可以进入实现阶段的条件：

- 所有 FR-01 至 FR-12 都有对应的结构、流程和验证方式。
- 数据模型与需求规格一致。
- 存储失败和损坏场景有明确处理。
- 主要交互流程没有未定义状态。
- 没有把第一版非目标功能混入实现范围。
- 用户确认本设计文档。
