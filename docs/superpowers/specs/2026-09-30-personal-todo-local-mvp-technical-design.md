# 个人本地待办应用设计文档（MVP 与扩展设计）

日期：2026-09-30  
状态：MVP 已确认；扩展设计待确认  
版本：1.3  
依据：`2026-09-30-personal-todo-local-mvp-design.md`

## 1. 设计目标

本设计文档说明个人本地待办应用 MVP 的技术结构、组件边界、数据流和验证方式，用于指导后续实现。

设计必须满足以下目标：

- 完全支持需求规格中的 FR-01 至 FR-12。
- 数据只保存在当前浏览器中，不需要后端。
- 不需要安装依赖，不引入框架和构建工具。
- 页面可以直接作为静态站点运行。
- 主要逻辑边界清晰，便于测试和以后扩展。
- 第一版代码保持精简，不实现需求之外的通用功能。

## 2. 设计约束

- 使用 HTML、CSS 和原生 JavaScript。
- 使用浏览器 `localStorage` 保存任务。
- 使用单页结构，不引入前端路由。
- 不引入组件库、状态管理库、测试框架或打包器。
- 用户输入只能作为纯文本渲染，不能作为 HTML 执行。
- 所有数据属于当前浏览器的当前站点来源，不提供跨设备同步。
- 第一版必须适配常见桌面和手机宽度。

## 3. 总体架构

应用采用简单的三层结构：

1. 表现层：HTML 负责页面结构，CSS 负责布局和状态样式。
2. 应用层：JavaScript 负责应用状态、事件处理、数据转换和界面渲染。
3. 存储层：JavaScript 中的本地存储适配逻辑负责读写 `localStorage`。

```text
用户操作
   |
   v
DOM 事件
   |
   v
应用状态更新
   |
   +--> 本地存储保存
   |
   v
重新渲染受影响的界面
```

应用不拆分后端服务，不拆分数据库，也不建立网络请求层。所有数据流都在当前页面内完成。

## 4. 文件结构

第一版采用三个运行时文件：

```text
/
├── index.html
├── styles.css
└── app.js
```

职责划分：

| 文件 | 职责 |
| --- | --- |
| `index.html` | 页面语义结构、输入区域、筛选区域、列表挂载点和状态提示区域 |
| `styles.css` | 基础视觉、布局、响应式、完成状态、空状态和焦点样式 |
| `app.js` | 应用状态、数据校验、任务操作、存储读写、渲染和事件处理 |

`app.js` 内部按职责分区，但不为了单页 MVP 建立额外模块或复杂抽象。

建议的逻辑顺序：

1. 常量和 DOM 引用
2. 存储适配
3. 数据校验和转换
4. 状态操作
5. 渲染函数
6. 事件处理
7. 初始化

## 5. 应用状态

应用运行时使用一个内存状态对象：

```text
appState
├── tasks: Task[]
├── filter: "all" | "active" | "completed"
├── editingTaskId: string | null
├── storageAvailable: boolean
└── storageNotice: string | null
```

状态说明：

| 字段 | 是否持久化 | 说明 |
| --- | --- | --- |
| `tasks` | 是 | 用户当前的全部任务 |
| `filter` | 否 | 当前筛选条件，刷新后恢复为 `all` |
| `editingTaskId` | 否 | 当前正在编辑的任务标识 |
| `storageAvailable` | 否 | 当前环境是否可以使用本地存储 |
| `storageNotice` | 否 | 需要向用户显示的存储异常提示 |

`filter` 和 `editingTaskId` 属于界面状态，不写入本地存储。`tasks` 是唯一需要跨页面刷新保存的数据。

## 6. 数据模型

### 6.1 持久化结构

`localStorage` 使用固定键名：

```text
personal-todo.mvp.v1
```

键名保持不变，避免升级时丢失用户现有数据；实际数据结构版本以负载中的 `version` 为准。

存储值使用一个带版本号的 JSON 对象。截止时间扩展使用版本 `2`：

```json
{
  "version": 2,
  "tasks": [
    {
      "id": "task-id",
      "title": "完成第一版",
      "completed": false,
      "createdAt": "2026-09-30T10:00:00.000Z",
      "updatedAt": "2026-09-30T10:00:00.000Z",
      "dueAt": "2026-10-01T10:00:00.000Z"
    }
  ]
}
```

### 6.2 任务对象

任务对象必须包含以下字段：

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | string | 非空且唯一 |
| `title` | string | 去除首尾空格后非空 |
| `completed` | boolean | `true` 表示已完成 |
| `createdAt` | string | 有效的 ISO 8601 时间字符串 |
| `updatedAt` | string | 有效的 ISO 8601 时间字符串 |
| `dueAt` | string 或 null | `null` 表示未设置；非空时必须是有效 ISO 8601 字符串 |

任务创建顺序和显示顺序分开处理。任务数组保存原始数据，渲染时统一按 `createdAt` 倒序排列，最新任务显示在最上方。

截止时间不参与默认排序。逾期状态由 `dueAt`、`completed` 和当前时间计算，不单独持久化。

### 6.3 标识生成

优先使用浏览器提供的 `crypto.randomUUID()`。

如果运行环境不支持，则使用当前时间戳和随机数组合生成一个在当前任务集合中不重复的字符串。第一版不需要引入 UUID 依赖。

## 7. 存储设计

### 7.1 读取

页面初始化时执行以下步骤：

1. 检查 `window.localStorage` 是否可访问。
2. 读取固定键名对应的字符串。
3. 如果字符串不存在，返回空的版本 2 数据结构。
4. 如果字符串可以被解析，则验证版本号和任务数组结构。
5. 如果版本为 `1`，将每个任务补充 `dueAt: null` 后迁移为版本 `2`。
6. 如果解析或验证失败，返回空任务列表并设置存储提示。

读取和验证必须是纯数据操作，不直接操作页面元素。

### 7.2 写入

每次任务数据发生变化后执行写入：

- 添加任务后
- 修改任务标题或截止时间后
- 切换完成状态后
- 删除任务后

写入失败时，内存中的任务仍然保留，当前页面继续可用，同时显示“数据无法永久保存”的提示。

### 7.3 数据校验

读取后的数据必须经过统一校验：

- 顶层对象必须包含正确的 `version`。
- `tasks` 必须是数组。
- 每个任务必须具有合法字段和正确类型。
- `title` 去除空格后不能为空。
- `id` 必须是字符串且不能重复。
- `createdAt` 和 `updatedAt` 必须是可解析的时间字符串。
- `dueAt` 必须是 `null` 或有效的时间字符串。
- 版本 1 数据按照迁移规则转换为版本 2，而不是判定为损坏。

第一版采用整体校验策略。如果顶层结构损坏，则回退到空列表，而不是尝试保留部分不可靠数据。

### 7.4 存储不可用

如果浏览器禁用本地存储、访问抛出异常或保存配额不足：

- 应用继续使用内存状态。
- 任务操作在当前会话内仍然有效。
- 页面显示明确的非阻断提示。
- 不通过弹窗中断用户操作。
- 不清除原始存储内容。

## 8. 界面组件

应用由以下逻辑组件组成：

### 8.1 AppShell

负责页面标题、主要内容容器和全局提示区域。

### 8.2 AddTaskForm

包含：

- 带明确标签的任务输入框
- 带明确标签的可选截止时间输入项
- 添加按钮
- 输入错误提示区域

行为要求：

- 提交时去除输入首尾空格。
- 截止时间为空时创建无期限任务。
- 非空截止时间转换为 ISO 8601 后保存。
- 空输入不产生任务。
- 提交成功后清空任务标题和截止时间并重新聚焦任务输入框。
- 支持 Enter 和按钮两种提交方式。

### 8.3 FilterBar

包含三个互斥选项：

- 全部
- 未完成
- 已完成

当前选项必须有可见选中状态，并提供可被辅助技术识别的状态。

### 8.4 TaskList

负责根据 `filter` 显示任务或空状态。

空状态分为两种情况：

- 完全没有任务：提示先添加一个任务。
- 当前筛选没有结果：提示该筛选条件下暂无任务。

### 8.5 TaskItem

单个任务项包含：

- 完成复选框
- 任务标题
- 截止时间文本和逾期状态
- 编辑按钮
- 删除按钮

编辑状态下，任务标题替换为文本输入框，截止时间替换为本地日期时间输入框，并显示保存和取消操作。

截止时间显示规则：

- 未设置时不显示期限区域。
- 已设置时显示本地化的年月日、小时和分钟。
- 未完成且 `dueAt` 早于当前时间时显示“已逾期”。
- 已完成时始终不显示逾期。

### 8.6 StatusSummary

显示未完成任务数量，例如：

```text
还有 3 项未完成
```

数量必须随任务状态变化即时更新。

### 8.7 StorageNotice

当本地存储不可用、读取失败或保存失败时显示提示。正常状态下不占用视觉空间。

## 9. 页面布局

页面采用居中的单列布局：

1. 标题和简短说明
2. 添加任务表单
3. 筛选栏
4. 任务列表或空状态
5. 剩余任务统计
6. 存储异常提示

桌面端：

- 主内容区设置合理最大宽度。
- 添加表单使用任务标题、截止时间和按钮的横向布局。
- 任务项使用复选框、内容区和操作区的三列布局。
- 长标题占用剩余空间并正常换行。

手机端：

- 主内容区保留安全边距。
- 任务标题、截止时间和添加按钮按纵向排列。
- 任务操作区保持可点击尺寸。
- 任务标题、截止时间、复选框和操作按钮不得相互遮挡。

视觉上使用安静的工具型风格，使用系统字体和有限的中性色。主操作使用一个强调色，完成状态、错误状态和普通状态必须有足够对比度。

## 10. 渲染策略

第一版使用简单、可预测的完整列表重渲染策略。

任务数据变化后：

1. 更新内存中的 `tasks`。
2. 写入本地存储。
3. 根据状态重新计算当前筛选结果。
4. 更新列表、剩余数量和空状态。

筛选条件变化和编辑状态变化只触发重新渲染，不触发存储写入。

渲染时使用 DOM 文本节点或 `textContent` 写入任务标题，禁止将用户输入拼接到 `innerHTML`。

列表事件使用事件委托，由 `TaskList` 统一处理完成、编辑、保存、取消和删除操作，避免为每次重渲染绑定无法追踪的重复监听器。

逾期样式由当前时间计算。页面打开后不启动定时器；刷新、筛选或任意数据变化触发重新渲染时重新计算逾期状态。

## 11. 关键流程

### 11.1 初始化

```text
页面加载
  -> 检查存储能力
  -> 读取并校验存储数据
  -> 建立 appState
  -> 绑定事件
  -> 渲染页面
```

初始化失败时必须进入可用状态。任务列表可以为空，但页面不能因为存储异常而停止工作。

### 11.2 添加任务

```text
提交输入
  -> 读取并 trim 标题
  -> 读取可选截止时间
  -> 转换为 ISO 8601 或 null
  -> 标题为空则显示验证提示
  -> 创建完整任务对象
  -> 加入 tasks 顶部或按时间排序
  -> 保存
  -> 重新渲染
  -> 清空任务输入和截止时间输入
  -> 聚焦任务输入框
```

### 11.3 切换完成状态

```text
点击复选框
  -> 找到目标任务
  -> 切换 completed
  -> 更新 updatedAt
  -> 保存
  -> 重新渲染
```

如果当前筛选为“未完成”，刚完成的任务会从列表中移除。如果当前筛选为“已完成”，取消完成后任务会从列表中移除。

### 11.4 编辑任务

```text
点击编辑
  -> 设置 editingTaskId
  -> 将该任务切换为输入状态
  -> 用户保存或取消
```

保存时：

```text
读取编辑值
  -> trim
  -> 空值提示并保持编辑状态
  -> 读取并转换截止时间
  -> 更新 title、dueAt 和 updatedAt
  -> 保存
  -> 清除 editingTaskId
  -> 重新渲染
```

取消时恢复原任务内容，不修改存储。

### 11.5 删除任务

```text
点击删除
  -> window.confirm 确认
  -> 用户确认后删除任务
  -> 保存
  -> 重新渲染
```

用户取消确认时不修改任务数据。

### 11.6 筛选任务

```text
点击筛选选项
  -> 更新 filter
  -> 重新计算可见任务
  -> 重新渲染列表和空状态
```

筛选不修改任务，不写入本地存储。

## 12. 异常处理

| 场景 | 处理方式 |
| --- | --- |
| 空标题 | 阻断提交，显示输入提示，保留输入焦点 |
| 截止时间为空 | 合法，保存为 `null` |
| 截止时间无法转换 | 阻断保存并显示输入提示 |
| 版本 1 数据 | 自动迁移为版本 2，原任务保留且 `dueAt` 为 `null` |
| 版本 2 的 `dueAt` 非法 | 按损坏数据整体回退 |
| 标题过长 | 正常保存，界面负责换行 |
| 存储不可用 | 切换为内存模式，显示非阻断提示 |
| 存储数据无法解析 | 使用空列表，显示提示，不崩溃 |
| 顶层结构版本不匹配 | 使用空列表并提示数据无法读取 |
| 保存失败 | 保留内存数据，提示无法永久保存 |
| 删除目标不存在 | 忽略该操作，重新渲染当前有效状态 |
| 编辑目标不存在 | 退出编辑状态，重新渲染当前有效状态 |
| 重复点击提交 | 提交过程中使用同步状态更新，避免重复任务 |
| 数字或特殊字符标题 | 作为普通纯文本处理 |

## 13. 无障碍设计

- 使用语义化 `header`、`main`、`form`、`button`、`ul` 和 `li`。
- 输入框必须有关联的 `label`。
- 截止时间输入项必须有关联的 `label`。
- 添加按钮、编辑按钮和删除按钮必须有可理解的可访问名称。
- 复选框使用原生元素，保证键盘可操作。
- 当前筛选状态不能只依赖颜色，必须有文字或 `aria-pressed` 等状态。
- 剩余数量和存储提示使用适当的 `aria-live` 区域。
- 所有交互元素必须有清晰的键盘焦点样式。
- 保持合理的文本和背景对比度。

## 14. 响应式设计

目标宽度范围：

- 最小支持宽度：320px
- 常见手机宽度：375px 至 430px
- 常见桌面宽度：1024px 及以上

响应式规则：

- 使用流式宽度和 `max-width`，不依赖固定页面宽度。
- 任务标题允许换行并使用 `overflow-wrap` 处理长单词或连续字符。
- 操作按钮保持稳定尺寸，不能被标题挤压。
- 在窄屏下允许添加区域从横向排列切换为纵向排列。
- 页面主要内容不得产生不必要的横向滚动。

## 15. 安全与隐私

- 所有任务内容只作为纯文本处理。
- 不将用户输入直接插入 HTML。
- 不发送网络请求。
- 不收集分析数据。
- 不写入浏览器外的位置。
- 清除站点数据后，本地任务会一并消失，这是当前设计接受的限制。

## 16. 测试设计

### 16.1 数据层验证

重点验证：

- 空存储读取
- 正确结构读取
- JSON 解析失败
- 版本号不匹配
- 版本 1 到版本 2 的迁移
- 任务字段类型错误
- `dueAt` 为 `null`、有效时间字符串和非法值
- 重复标识处理
- 添加、修改、完成和删除后的写入
- 存储写入失败时的内存回退

### 16.2 交互验证

重点验证：

- Enter 添加
- 按钮添加
- 空内容添加
- 只有空格的内容添加
- 添加带截止时间的任务
- 添加不带截止时间的任务
- 编辑和清除截止时间
- 逾期状态和已完成任务的非逾期状态
- 完成和取消完成
- 编辑保存和取消
- 编辑为空时不能保存
- 删除确认和取消
- 三类筛选切换
- 空状态和无筛选结果状态
- 剩余数量更新

### 16.3 浏览器验证

至少检查：

- 页面加载无阻断错误
- 刷新后任务保持一致
- 本地存储损坏后页面仍可用
- 320px 手机宽度下无重叠和横向溢出
- 桌面宽度下排版正常
- 键盘可以完成主要操作

第一版不强制引入自动化测试框架。为了保留后续自动化空间，数据校验和任务转换逻辑应保持为清晰、可独立调用的函数。

## 18. 设计取舍

选择原生静态方案的原因：

- MVP 只有单页面和少量交互。
- 数据完全属于当前浏览器，不需要网络层。
- 无依赖方案更容易直接运行和排查问题。
- 当前功能不需要组件框架或状态管理库。

有意保持简单的地方：

- 使用完整列表重渲染，不建立虚拟 DOM。
- 使用 `window.confirm` 删除确认，不实现自定义弹窗。
- 使用 `localStorage`，不引入 IndexedDB。
- 只持久化任务，不持久化筛选和编辑状态。
- 截止时间只保存 `dueAt`，不保存提醒状态或完成时间。
- 逾期状态按当前时间派生，不写入存储。
- 不建立通用存储接口，只保留一个小的存储适配区域。

这些取舍符合当前规模。只有当数据量、协作能力或同步需求真正出现时，才考虑引入更复杂的存储和组件结构。

## 19. 后续扩展方向

以下内容不属于第一版，但当前结构应允许未来扩展：

- 为任务增加提醒、优先级和标签字段。
- 将 `localStorage` 适配替换为后端 API。
- 增加账号和云同步。
- 增加搜索、排序和拖拽。
- 增加自动化测试和持续集成。

扩展时继续遵循一个原则：先修改需求规格和设计文档，再修改实现。

## 20. 设计完成标准

本设计可以进入实现阶段的条件：

- 所有 FR-01 至 FR-12 都有对应的结构、流程和验证方式。
- 数据模型与需求规格一致。
- 存储失败和损坏场景有明确处理。
- 主要交互流程没有未定义状态。
- 没有把第一版非目标功能混入实现范围。
- 用户确认本设计文档。

## 21. 扩展设计目标与边界

扩展设计覆盖需求规格中的 EXT-01 至 EXT-14。扩展仍然遵守以下原则：

- 个人本地优先，不引入账号和云端服务。
- 先保证任务数据可迁移、可恢复，再增加新界面。
- 纯数据逻辑与 DOM、存储和通知 API 分离。
- 每个阶段独立设计、独立迁移、独立测试。
- 不把所有扩展能力一次性加入同一个发布版本。
- 提醒、重复任务和日历所依赖的时间语义必须保持一致。

扩展设计不改变当前 MVP 已完成的功能。现有版本 2 任务必须可以无损迁移。

│   ├── sortBy: SortField

## 24. 扩展数据模型

### 24.1 顶层数据结构

扩展后的存储负载建议为：

```json
{
  "version": 3,
  "tasks": [],
  "categories": [],
  "tags": [],
  "preferences": {
    "theme": "system",
    "view": "all",
    "sortBy": "manual",
    "sortDirection": "asc"
  }
}
```

顶层 `version` 必须随新增字段升级。现有 `personal-todo.mvp.v1` 键名继续保留，仅改变负载版本。

### 24.2 扩展任务对象

扩展任务对象字段：

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 无 | 唯一标识 |
| `title` | string | 无 | 非空标题 |
| `completed` | boolean | `false` | 当前任务是否完成 |
| `createdAt` | string | 当前时间 | ISO 8601 |
| `updatedAt` | string | 当前时间 | ISO 8601 |
| `startAt` | string 或 null | `null` | 计划开始时间 |
| `dueAt` | string 或 null | `null` | 截止时间 |
| `recurrence` | object | 一次规则 | 重复规则 |
| `reminders` | array | `[]` | 提醒规则 |
| `categoryId` | string 或 null | `null` | 单分类关联 |
| `tagIds` | string array | `[]` | 多标签关联 |
| `priority` | string | `"none"` | 优先级枚举 |
| `notes` | string | `""` | 多行纯文本 |
| `subtasks` | array | `[]` | 子任务集合 |
| `completionCount` | number | `0` | 完成次数 |
| `manualOrder` | number | 自动生成 | 手动排序序号 |
| `seriesId` | string 或 null | `null` | 重复任务系列标识 |
| `focusSessions` | array | `[]` | 专注计时记录 |

字段必须通过迁移加入，不允许读取时静默猜测。

### 24.3 重复规则

```text
recurrence
├── mode: "once" | "daily" | "weekly"
├── weekdays: number[]
└── timeZone: string
```

约束：

- `once` 表示不重复。
- `daily` 默认按每天同一本地时间重复。
- `weekly` 的 `weekdays` 使用 `0` 至 `6`，其中 `0` 表示周日。
- 周重复至少选择一天。
- `timeZone` 默认使用浏览器时区。
- 修改重复规则时，不修改已经发生的历史完成记录。

### 24.4 提醒规则

```text
reminder
├── id: string
├── anchor: "startAt" | "dueAt"
├── offsetMinutes: number
├── enabled: boolean
└── lastTriggeredAt: string | null
```

约束：

- `offsetMinutes` 为 `0` 表示准时提醒。
- 负数或固定枚举表示提前提醒，具体编码在实现阶段固定。
- 同一任务允许多个提醒。
- `lastTriggeredAt` 用于避免刷新页面后重复触发。
- 提醒只能在使用绝对时间或可重建为绝对时间的规则触发。

### 24.5 分类和标签对象

```text
Category
├── id
├── name
├── color
└── createdAt

Tag
├── id
├── name
├── color
└── createdAt
```

分类和标签使用独立集合，任务只保存标识引用。删除分类或标签时必须先执行关联清理。

### 24.6 子任务对象

```text
Subtask
├── id
├── title
├── completed
└── order
```

子任务属于父任务，不建立独立顶层集合。进度为：

```text
completedSubtasks / totalSubtasks
```

## 25. 存储版本与迁移策略

建议按阶段升级：

| 版本 | 新增内容 | 迁移默认值 |
| --- | --- | --- |
| `3` | 分类、标签、优先级、备注、完成次数、手动顺序、偏好设置 | 空分类、空标签、`priority: "none"`、`notes: ""`、`completionCount: 0` |
| `4` | 开始时间、重复规则、提醒、子任务 | `startAt: null`、`recurrence: once`、`reminders: []`、`subtasks: []` |
| `5` | 专注计时记录 | `focusSessions: []` |

迁移原则：

- 每次只增加该阶段真正使用的字段。
- 迁移函数必须按版本顺序执行。
- 迁移前先校验源数据结构。
- 迁移后再次校验目标结构。
- 任一迁移失败时保留原存储内容，并提示用户。
- 不覆盖无法解析的未知版本数据。

## 26. 查询、视图和排序设计

扩展查询使用单向流水线：

```text
全部任务
  -> 视图过滤
  -> 状态过滤
  -> 分类过滤
  -> 标签过滤
  -> 优先级过滤
  -> 搜索
  -> 排序
  -> 可见任务
```

约束：

- 每一步返回新数组，不修改原始任务集合。
- 过滤条件之间使用 AND，同一多选维度内部使用 OR。
- 搜索对标题、备注、分类名称和标签名称执行规范化匹配。
- 排序结果必须有稳定的最终比较项，例如 `id`。
- 自动排序不修改 `manualOrder`。
- 手动排序只在手动排序模式应用。

建议视图：

| 视图 | 计算方式 |
| --- | --- |
| 全部 | 所有未删除任务 |
| 今日 | `dueAt` 或 `startAt` 落在本地当天 |
| 即将到期 | 尚未完成且在未来时间窗口内，默认窗口需确认 |
| 已完成 | `completed === true` |
| 已逾期 | 未完成且 `dueAt < now` |
| 分类 | `categoryId` 匹配当前分类 |
| 标签 | `tagIds` 包含任意当前标签 |

搜索和排序状态不应直接改变任务对象。

## 27. 时间、重复和提醒设计

### 27.1 时间规则

- 用户界面使用 24 小时制。
- 输入值按浏览器本地时区解释。
- 存储使用 ISO 8601 字符串。
- 所有时间计算接收显式 `now`，便于测试。
- 今日视图以本地日界线计算，不按 UTC 日界线切割。

### 27.2 重复任务

推荐使用“系列任务 + 完成记录”的设计：

```text
TaskSeries
├── id
├── recurrence
└── occurrenceTemplate

TaskOccurrence
├── id
├── seriesId
├── occurrenceAt
├── completed
└── completedAt
```

第一轮实现也可以先把周期规则直接保存在任务上，但必须保留 `seriesId`，避免后续迁移时无法区分重复发生实例。

完成重复任务时：

1. 记录当前发生实例的完成状态和完成时间。
2. 根据规则计算下一次发生时间。
3. 如果下一次实例不存在，则创建或显示下一次任务。
4. 不覆盖历史完成记录。

删除时需要提供范围选择：

- 仅删除当前实例
- 删除当前及后续实例
- 删除整个系列

### 27.3 提醒引擎

用户已经确认提醒必须在浏览器关闭后尽可能继续生效。因此采用以下组合：

1. 前台页面模式：页面打开时使用运行时调度，刷新后根据 `lastTriggeredAt` 补算未触发提醒。
2. 后台推送模式：使用 Service Worker、Web Push 和最小提醒后端；后端保存提醒计划和订阅，在目标时间向浏览器推送通知。

后台推送模式是系统级提醒的正式实现路径。它需要后端服务、HTTPS、VAPID 密钥、提醒调度器和 Web Push 订阅，不再满足原先“完全没有后端、任务数据完全不离开浏览器”的静态边界。

仍然存在平台限制：

- Web Push 不能在所有操作系统和浏览器上获得与原生闹钟完全相同的交付保证。
- 用户禁用通知、浏览器限制后台活动、系统省电模式和推送服务故障都可能造成延迟或漏发。
- 如果产品要求合同级别的“必定触发”，需要在后续阶段增加原生桌面或移动端应用，或者接入操作系统日历与本地通知。

设计边界：

- 没有 Service Worker 和通知权限时，不承诺浏览器关闭后的提醒。
- 通知权限必须由用户主动授权。
- 同一条提醒在未修改规则前只能触发一次。
- 修改开始时间、截止时间或重复规则后，需要重新计算未完成的提醒任务。
- 系统时间变化、浏览器休眠和后台节流必须考虑，不能依赖单次 `setTimeout`。

提醒是否能满足“系统闹钟”级别，是后续实现的架构门槛，不由界面层自行决定。

## 28. 任务结构功能设计

### 28.1 分类和标签

- 分类是单值关联，标签是多值关联。
- 分类和标签通过独立管理界面新增、重命名和删除。
- 删除分类时，用户选择迁移任务或设为未分类。
- 删除标签时，只从任务中移除引用。
- 默认分类为生活、学习，默认标签可以包括吃饭、健身、阅读、编程和复习。
- 默认值只在首次初始化时写入，不能在每次加载时重复创建。

### 28.2 优先级

优先级枚举：

```text
none < low < medium < high < urgent
```

任务列表必须显示文字标签或无障碍名称。排序时使用明确的数值权重，不使用颜色顺序推断。

### 28.3 任务备注

- 使用纯文本字段保存。
- 保留换行，不在输入和输出时自动合并空白。
- 通过 `textContent` 渲染。
- 参与搜索，不参与默认显示。
- 为空时不渲染备注容器。

### 28.4 子任务和进度

- 子任务编辑独立于父任务完成状态。
- 进度由子任务数组即时计算，不单独持久化。
- 父任务默认不因全部子任务完成而自动完成。
- 删除子任务不影响父任务标题、备注和其他字段。

## 29. 手动排序和拖拽设计

- `manualOrder` 是持久化数值字段。
- 在手动排序模式下拖拽后重新计算受影响任务顺序。
- 任务数量较小时可以直接重新编号，不引入复杂排序算法。
- 拖拽事件只修改 `manualOrder`，不修改 `createdAt`。
- 自动排序模式禁用拖拽。
- 键盘用户可以使用上移、下移按钮。
- 手机端提供触摸拖拽或等价的排序按钮。

## 30. 视图和辅助功能设计

### 30.1 今日、即将到期和已逾期

- 今日视图显示本地当天范围内的任务。
- 已逾期视图只显示未完成且超过截止时间的任务。
- 即将到期的默认窗口需要在设计确认时固定，例如未来 3 天或 7 天。
- 所有视图使用同一查询流水线。

### 30.2 深色模式

- 使用 `data-theme` 属性切换主题。
- 使用 CSS 变量定义颜色，不在组件内写固定浅色值。
- `system` 模式通过 `matchMedia("(prefers-color-scheme: dark)")` 跟随系统。
- 用户手动选择应持久化。

### 30.3 键盘快捷键

- 快捷键集中注册，不在各组件散落监听。
- 当焦点位于输入框、文本域或可编辑元素时，不拦截普通字符。
- 快捷键需要帮助面板。
- 主要操作必须同时有鼠标和触摸入口。

### 30.4 日历视图

- 日历只读取任务数据，不建立第二份任务状态。
- 首轮可以先实现月视图和当天任务列表。
- 重复任务按发生实例计算。
- 日期计算必须复用时间规则模块。

### 30.5 专注计时器

- 计时状态与任务持久化状态分离。
- 使用开始时间计算已用时长，不依赖页面刷新期间的递增计数器。
- 结束时新增一条专注记录。
- 计时器停止后不影响任务完成状态。

## 31. 扩展错误处理

| 场景 | 处理方式 |
| --- | --- |
| 分类不存在 | 显示为未分类，不删除任务 |
| 标签不存在 | 从任务标签引用中移除或显示未知标签 |
| 重复规则非法 | 阻止保存，保留原规则 |
| 提醒时间早于当前时间 | 允许保存，但根据规则不补触发或只触发一次 |
| 通知权限被拒绝 | 保留应用内提醒，不反复请求权限 |
| 页面在提醒前关闭 | 进入后台能力评估，不静默承诺通知 |
| 拖拽顺序冲突 | 使用稳定排序和最终编号修复 |
| 搜索无结果 | 显示当前条件无结果的空状态 |
| 迁移失败 | 保留原数据，显示错误，不覆盖 |
| 主题偏好无效 | 回退到系统主题 |

## 32. 扩展性能和规模

- 纯过滤、搜索和排序在当前本地规模下直接执行，不建立索引服务。
- 每次查询结果使用一次完整重渲染，必要时再优化局部更新。
- 拖拽过程中只在内存中更新临时顺序，放下后才持久化。
- 提醒调度只保存未来或未触发提醒，不扫描无限历史。
- 日历只计算当前显示范围。
- 当任务数量达到明显影响交互的规模时，再评估虚拟列表和索引。

## 33. 扩展无障碍和响应式要求

- 分类、标签、优先级、进度和提醒状态不能只依赖颜色。
- 子任务复选框、排序按钮和提醒开关必须支持键盘。
- 拖拽必须有非拖拽替代操作。
- 弹出菜单和日期选择器必须管理焦点。
- 手机端不能同时显示过多控制项，筛选和排序应进入可展开面板。
- 日期、提醒和重复规则在 320px 宽度下不能产生横向滚动。
- 深色模式必须保持可访问对比度。

## 36. 扩展设计完成标准

进入某个扩展阶段实现前，必须满足：

- 对应 EXT 需求和待确认问题已经确认。
- 数据模型和迁移版本已经确定。
- 模块边界和接口已经写入设计。
- 查询、排序或提醒算法有独立测试设计。
- 交互流程、错误处理和空状态已经定义。
- 无障碍和移动端方案已经定义。
- 前一阶段已经完成测试和验收。

扩展设计仍然等待用户确认的项目包括：

- “次数”字段的最终定义。
- 重复任务完成后的历史记录策略。
- 父任务和子任务的完成联动。
- 分类和标签是否允许完整自定义。
- 今日和即将到期视图的具体时间窗口。
- 日历视图的首轮粒度。
- 专注计时器是否保存统计历史。
