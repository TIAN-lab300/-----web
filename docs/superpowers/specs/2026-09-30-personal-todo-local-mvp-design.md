# 个人本地待办应用需求规格说明（MVP 与扩展规划）

> 提醒功能已从项目范围删除。本应用只保留重复规则，不包含通知、Web Push、Service Worker、VAPID 或后台提醒服务。

日期：2026-09-30  
状态：MVP 已确认；扩展规划待确认  
版本：0.4

## 1. 项目概述

本项目是一个面向个人使用的本地待办 Web 应用。用户可以在浏览器中记录任务、完成任务、编辑任务、删除任务，并按状态筛选任务。所有数据只保存在当前浏览器中，不上传服务器，不需要注册或登录。

第一版的目的是完成一个简单、稳定、可直接使用的 MVP，而不是一次性加入全部待办应用功能。

## 2. 目标

- 让用户可以快速记录待办事项。
- 让用户可以清楚地看到未完成和已完成的任务。
- 让用户可以为任务设置并查看自定义截止时间。
- 让任务在刷新页面或重新打开浏览器后仍然存在。
- 提供一个适合桌面和手机浏览器的简洁界面。
- 保持实现简单，不需要后端、账号系统或第三方服务。

## 3. 非目标

以下内容不属于当前 MVP 范围。其中部分功能已经列入第 16 至 21 节的扩展规划，但不会自动进入当前版本：

- 用户注册、登录和权限控制
- 云端同步和多设备同步
- 多人共享和个人协作
- 优先级、标签、分类和备注
- 子任务、重复任务和日历视图
- 搜索、排序和拖拽调整顺序
- 数据导入、导出和跨浏览器迁移
- 离线 PWA、安装到桌面和后台同步
- AI 自动拆解任务或智能推荐

## 4. 目标用户

主要用户是希望用浏览器管理个人任务的单用户。

典型使用场景：

1. 用户打开页面，输入一个待办事项。
2. 用户查看当前未完成的任务。
3. 用户完成某项任务后，将其标记为已完成。
4. 用户通过筛选器查看全部、未完成或已完成任务。
5. 用户关闭浏览器，之后再次打开，任务仍然存在。

## 5. 用户故事

- 作为用户，我希望能添加任务，以便记住需要完成的事情。
- 作为用户，我希望能一次看到所有任务，以便了解当前待办情况。
- 作为用户，我希望标记任务完成，以便区分已完成和未完成事项。
- 作为用户，我希望修改任务文字，以便纠正输入错误或更新内容。
- 作为用户，我希望为任务设置或修改截止时间，以便明确任务的期限。
- 作为用户，我希望看到任务是否已经逾期，以便优先处理。
- 作为用户，我希望删除任务，以便移除不再需要的事项。
- 作为用户，我希望按状态筛选任务，以便只查看当前关心的内容。
- 作为用户，我希望数据自动保存，以便刷新页面后不丢失任务。
- 作为用户，我希望在手机上也能正常使用。

## 6. 功能需求

### FR-01 添加任务

- 页面必须提供一个任务输入框和一个明确的添加按钮。
- 页面必须提供一个自定义截止时间输入项。
- 创建任务时，任务名称、截止时间和优先级必须填写。
- 创建任务时，优先级不能选择“无”。
- 用户输入非空文字后，可以点击按钮或按 Enter 添加任务。
- 添加前必须去除任务标题首尾空格。
- 空内容或只有空格的内容不能创建任务。
- 新任务默认状态为未完成。
- 截止时间是创建任务的必填项。
- 添加成功后，输入框必须清空并重新获得焦点。
- 添加成功后，截止时间输入项也必须清空。
- 每个任务必须有唯一标识、创建时间和更新时间；截止时间可以为空。

### FR-02 显示任务列表

- 页面必须显示当前筛选条件下的任务列表。
- 每个任务必须显示复选框、任务标题和删除操作。
- 设置了截止时间的任务必须显示本地化的日期和时间。
- 未完成且已超过截止时间的任务必须显示“已逾期”状态。
- 已完成任务不显示逾期状态。
- 未完成任务使用正常文字样式。
- 已完成任务使用删除线或明显的完成样式。
- 任务较多时，页面应自然滚动，不覆盖其他页面内容。

### FR-03 标记完成

- 用户可以通过任务前的复选框切换完成状态。
- 从已完成切换为未完成时，任务必须恢复为正常显示样式。
- 状态变化后必须自动保存。

### FR-04 编辑任务

- 用户必须可以修改已有任务的标题。
- 用户必须可以修改或清除已有任务的截止时间。
- 修改后的标题不能为空。
- 编辑成功后必须更新任务的截止时间和更新时间并自动保存。

### FR-05 删除任务

- 用户必须可以删除单个任务。
- 删除前应进行确认，避免误删。
- 删除后任务必须从列表和本地存储中移除。

### FR-06 筛选任务

页面必须提供以下筛选选项：

- 全部
- 未完成
- 已完成

当前筛选状态必须清晰可见。切换筛选后，列表只显示符合条件的任务。

### FR-07 剩余任务统计

- 页面必须显示未完成任务数量。
- 完成任务状态变化后，统计数量必须立即更新。

### FR-08 本地持久化

- 所有任务必须保存在当前浏览器的本地存储中。
- 页面加载时必须自动读取并恢复任务。
- 添加、编辑、完成、取消完成和删除操作后必须自动保存。
- 存储数据结构必须包含版本号，方便以后升级。
- 如果本地数据损坏或无法解析，应用应回退为空列表，并避免页面崩溃。

### FR-09 空状态

- 当没有任何任务时，页面必须显示友好的空状态提示。
- 当某个筛选条件下没有任务时，页面应显示该状态下的对应提示。

### FR-10 响应式界面

- 页面必须适配常见桌面和手机宽度。
- 输入框、筛选器、任务操作和文本不得相互遮挡。
- 长任务标题必须正确换行，不能溢出容器。

### FR-11 基础可用性

- 输入框必须支持键盘操作。
- 截止时间输入项必须支持键盘操作并有明确标签。
- 按钮必须具有可理解的文字或无障碍名称。
- 复选框必须可以通过键盘切换。
- 页面刷新后，当前任务数据必须保持一致。

### FR-12 自定义截止时间

- 用户可以在创建任务时自行设置截止时间。
- 用户可以在编辑任务时修改或清除截止时间。
- 截止时间使用浏览器本地日期和时间输入控件。
- 截止时间可以精确到分钟。
- 截止时间为空时，任务不显示期限信息。
- 截止时间不为空时，任务项必须显示完整日期和时间。
- 如果任务未完成且截止时间早于当前时间，页面必须显示“已逾期”。

## 7. 数据模型

本地存储建议使用以下结构：

```json
{
  "version": 2,
  "tasks": [
    {
      "id": "uuid-or-timestamp-string",
      "title": "完成第一版",
      "completed": false,
      "createdAt": "2026-09-30T10:00:00.000Z",
      "updatedAt": "2026-09-30T10:00:00.000Z",
      "dueAt": "2026-10-01T10:00:00.000Z"
    }
  ]
}
```

字段说明：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `version` | number | 是 | 存储结构版本，截止时间扩展使用 `2` |
| `tasks` | array | 是 | 任务集合 |
| `id` | string | 是 | 任务唯一标识 |
| `title` | string | 是 | 任务文字，不能为空 |
| `completed` | boolean | 是 | 是否已完成 |
| `createdAt` | string | 是 | 创建时间，ISO 8601 格式 |
| `updatedAt` | string | 是 | 最近修改时间，ISO 8601 格式 |
| `dueAt` | string 或 null | 是 | 用户设置的截止时间；未设置时为 `null` |

## 8. 页面结构

第一版建议使用单页结构：

1. 页面标题：个人待办
2. 添加任务区域：任务输入框、截止时间输入项和添加按钮
3. 筛选区域：全部、未完成、已完成
4. 任务列表区域
5. 底部统计区域：剩余未完成任务数量

任务项建议包含：

- 完成复选框
- 任务标题
- 截止时间及逾期状态
- 编辑操作
- 删除操作

## 9. 交互流程

### 添加任务

1. 用户输入任务标题。
2. 用户可以选择设置截止时间。
3. 用户按 Enter 或点击添加。
4. 系统去除首尾空格并验证内容。
5. 创建任务并保存。
6. 列表和剩余数量更新。
7. 任务输入框和截止时间输入项清空，任务输入框重新获得焦点。

### 完成任务

1. 用户点击任务复选框。
2. 系统切换完成状态并保存。
3. 任务样式和剩余数量更新。
4. 如果当前筛选条件不再匹配，任务从当前列表移除。

### 编辑任务

1. 用户进入编辑状态。
2. 用户修改标题、截止时间，或将截止时间清空。
3. 系统验证标题非空。
4. 系统保存修改并退出编辑状态。

### 删除任务

1. 用户点击删除。
2. 系统显示确认提示。
3. 用户确认后，任务被删除并保存。
4. 列表和剩余数量更新。

## 10. 异常和边界情况

- 输入内容为空时，不创建任务。
- 输入内容只有空格时，不创建任务。
- 截止时间为空时，任务可以正常创建。
- 截止时间可以按浏览器支持的本地日期时间格式输入。
- 任务已经标记为完成时，即使截止时间已过，也不显示逾期状态。
- 任务标题很长时，必须换行且不遮挡操作按钮。
- 本地存储为空时，显示空状态。
- 本地存储内容损坏时，不崩溃并回退为空列表。
- 删除不存在的任务时，不应影响其他任务。
- 浏览器不支持本地存储或存储被禁用时，页面应可用，但必须明确提示数据无法永久保存。

满足以下条件时，第一版视为完成：

1. 用户可以添加非空任务。
2. 空任务无法被添加。

4. 用户可以看到全部、未完成和已完成任务。
5. 用户可以标记任务完成或恢复为未完成。
6. 用户可以编辑任务标题，且空标题不能保存。
7. 用户可以删除任务，并在删除前看到确认提示。
8. 添加、编辑、完成、取消完成和删除后，数据会自动保存。
9. 刷新页面后，任务内容和状态保持不变。
10. 剩余未完成任务数量正确。
11. 空列表和筛选后无结果时显示对应提示。
12. 页面在常见手机和桌面浏览器宽度下可正常操作。
13. 本地数据损坏时页面不会崩溃。
14. 用户可以创建不带截止时间的任务。
15. 用户可以创建带自定义截止时间的任务。
16. 截止时间可以精确到分钟并正确保存。
17. 用户可以编辑或清除已有任务的截止时间。
18. 未完成且已过截止时间的任务显示“已逾期”。
19. 已完成任务不显示逾期状态。
20. 旧的版本 1 任务数据可以迁移为不含截止时间的版本 2 数据。
21. 创建任务时，缺少任务名称、截止时间或优先级时不能创建。
22. 创建任务时，优先级不能保持为“无”。

## 12. 技术方案

第一版采用最简单的本地静态 Web 方案：

- HTML：页面结构
- CSS：布局、响应式和视觉状态
- JavaScript：任务状态、交互和本地存储
- `localStorage`：数据持久化
- 不引入后端、数据库、框架和构建工具

这样可以降低第一版的运行和部署成本。未来如果需要账号或云同步，可以在保持页面交互不变的前提下增加后端和数据库。

## 17. 扩展功能详细需求

### EXT-01 时间戳和重复规则

时间设置：

- 用户可以在创建任务时设置开始时间或计划时间。
- 用户可以在创建任务时设置截止时间，也可以在创建后编辑。
- 截止时间使用 24 小时制显示和输入。
- 开始时间和截止时间必须使用同一套本地时间规则。
- 用户可以清除开始时间或截止时间。
- 设置截止时间后，任务列表必须显示本地化日期和时间。
- 未完成且已过截止时间的任务显示“已逾期”。
- 已完成任务不显示逾期状态。

重复规则：

- 默认重复方式为“一次”，即不重复。
- 支持“每天”重复。
- 支持“每周指定日期”重复，用户可以选择一周中的一天或多天。
- 重复规则必须支持编辑和取消。
- 每一次重复结束后，下一次任务日期必须按照所选规则计算。


重复和完成的关系：

- 用户完成一个重复任务后，应保留本次完成记录，并生成或显示下一次任务。
- 是否原地移动到下一次日期，或保留历史完成记录，需要按第 21 节确认。
- 删除重复任务时，应明确删除当前任务、后续重复或整个重复规则。

### EXT-02 分类

- 每个任务可以属于一个分类。
- 默认提供“生活”和“学习”两个分类。
- “生活”下可以包含“吃饭”“健身”等主题。
- “学习”下可以包含学习计划、课程、阅读等主题。
- 用户可以给任务设置“未分类”。
- 用户可以新增、重命名和删除自定义分类。
- 删除已有任务的分类时，不能删除任务本身。
- 删除分类时，需要要求用户选择将相关任务移动到其他分类或设为“未分类”。
- 分类可以用来筛选和排序任务。

### EXT-03 标签

- 每个任务可以有零个或多个标签。
- 标签和分类是两个独立概念，分类通常单选，标签可以多选。
- 默认可以提供“吃饭”“健身”“阅读”“编程”“复习”等标签。
- 用户可以新增、重命名和删除标签。
- 删除标签只会解除任务关联，不会删除任务。
- 标签可以用于搜索、筛选和排序。
- 标签名称不能为空，默认不区分大小写重复。

### EXT-04 优先级

- 每个任务可以设置优先级。
- 默认优先级为“无”。
- 初始优先级层级建议为“无、低、中、高、紧急”。
- 任务列表中必须显示非“无”的优先级状态。
- 优先级可以用于排序和筛选。
- 用户可以在创建和编辑任务时修改优先级。
- 优先级不能只依赖颜色表达，必须同时有文字或可访问名称。

### EXT-05 任务备注

- 每个任务可以包含一段较长的补充说明。
- 备注支持多行纯文本。
- 备注在创建和编辑任务时都可以修改。
- 备注必须随任务一起自动保存。
- 备注内容可以参与搜索。
- 第一版扩展不要求富文本、Markdown 渲染、图片或附件。
- 备注为空时，任务列表不显示备注区域。

### EXT-06 搜索

- 用户可以按关键词搜索任务。
- 搜索范围至少包括任务标题、备注、分类和标签。
- 搜索应支持部分匹配，例如输入“健”可以匹配“健身”。
- 搜索应支持中文和普通英文字符。
- 搜索可以与分类、标签、状态、优先级和时间筛选组合使用。
- 搜索无结果时必须显示明确的空状态。
- 清除搜索条件后，应恢复当前视图的完整任务列表。

### EXT-07 排序

排序需要至少支持以下维度：

- 按标签排序
- 按开始时间或截止时间排序
- 按创建时间或更新时间排序
- 按完成次数排序
- 按优先级排序
- 按手动顺序排序

排序规则：

- 每个排序维度应支持升序和降序，除非该维度只有单一合理方向。
- 排序可以与搜索和筛选组合使用。
- 使用自动排序时，不改变任务的手动顺序数据。
- 切换回手动排序时，应恢复用户之前保存的顺序。

### EXT-08 子任务和进度

- 每个任务可以包含零个或多个子任务。
- 子任务至少包含标题和完成状态。
- 用户可以新增、编辑、完成、取消完成和删除子任务。
- 子任务的顺序必须可以保存。
- 进度按照已完成子任务数除以子任务总数计算。
- 没有子任务的任务不显示进度条。
- 父任务和子任务的完成关系必须在实现前确认，默认建议父任务不自动完成。
- 完成全部子任务后可以显示完成提示，但不能静默改变父任务状态。

### EXT-09 拖拽调整顺序

- 用户可以拖拽任务调整列表顺序。
- 拖拽只在手动排序模式下生效。
- 调整后的顺序必须持久化。
- 搜索、筛选或切换到自动排序时，不允许误改原始手动顺序。
- 拖拽必须有键盘可用的替代操作，例如上移和下移。
- 在手机浏览器中必须支持触摸拖拽或提供等价的排序按钮。

### EXT-10 任务视图

扩展视图至少包括：

- 今日
- 即将到期
- 全部
- 已完成
- 已逾期
- 分类视图
- 标签视图

视图规则：

- 视图是由任务数据计算出来的，不重复保存任务。
- 切换视图不能修改任务数据。
- 每个视图应显示任务数量和空状态。
- 视图、筛选、搜索和排序组合后的结果必须一致且可解释。

### EXT-11 深色模式

- 支持浅色、深色和跟随系统三种模式。
- 用户选择必须持久化。
- 深色模式必须保持文本、按钮、截止时间、逾期和完成状态的对比度。
- 深色模式不能改变任务数据和交互流程。

### EXT-12 键盘快捷键

- 快捷键应覆盖新建任务、搜索、完成、编辑、删除、切换视图和打开帮助。
- 输入框处于编辑状态时，普通字符不能被全局快捷键拦截。
- 快捷键需要在界面中提供帮助入口。
- 快捷键不能成为唯一操作方式。

### EXT-13 日历视图

- 支持按日、周或月查看任务。
- 带开始时间或截止时间的任务显示在对应日期。
- 重复任务按照重复规则显示。
- 点击日历中的任务可以查看或编辑任务。
- 日历视图与列表视图必须使用同一份任务数据。
- 日历视图可以作为后续版本功能，不要求首轮扩展同时实现。

### EXT-14 专注计时器

- 用户可以将计时器关联到一个任务。
- 支持开始、暂停、继续和结束计时。
- 计时过程中显示已用时间。
- 结束计时后可以记录本次专注时长。
- 是否累加任务专注总时长、是否保留历史记录需要独立设计。
- 计时器不应阻塞任务的基本操作。

## 18. 扩展数据模型方向

扩展实现前，任务数据模型需要评估以下字段：

```text
Task
├── id
├── title
├── completed
├── createdAt
├── updatedAt
├── startAt
├── dueAt
├── recurrence
├── categoryId
├── tagIds
├── priority
├── notes
├── subtasks
├── completionCount
├── manualOrder
└── focusSessions
```

新增字段必须通过存储版本迁移加入。现有版本 2 任务在迁移时补充默认值，例如：

- `priority: "none"`
- `notes: ""`
- `tagIds: []`
- `subtasks: []`
- `completionCount: 0`

具体字段类型和存储版本在实现前写入设计文档和技术文档，不能直接在现有代码中静默加入未定义字段。

## 19. 扩展功能非功能性要求

- 所有扩展功能继续遵守个人本地优先原则。
- 任何数据迁移都必须保留现有任务。
- 新增筛选和排序不能破坏已完成、未完成和截止时间逻辑。
- 大任务数量下必须保持可接受的首屏和交互性能。
- 所有新交互必须支持键盘和触摸操作。
- 所有新状态不能只依赖颜色表达。
- 搜索和排序结果必须稳定且可重复。
- 浏览器通知能力必须经过用户授权，不能默认开启。
- 不能因为新增功能导致原有任务丢失或无法读取。

## 20. 建议实施阶段

建议按依赖关系分阶段实施，避免一次改动全部数据模型和界面：

### 阶段 A：任务组织基础

- 优先级
- 任务备注
- 分类
- 标签

### 阶段 B：查找和视图

- 搜索
- 排序
- 今日、即将到期、全部和已完成视图
- 深色模式

### 阶段 C：任务结构优化

- 子任务和进度
- 拖拽排序
- 键盘快捷键

### 阶段 D：时间自动化

- 开始时间
- 重复规则

### 阶段 E：复杂视图

- 日历视图
- 专注计时器

阶段可以调整，但每次只实现一个阶段，并单独完成需求、设计、技术文档、测试和验收。

## 21. 扩展规划待确认事项

以下问题会影响数据模型和交互，必须在进入对应阶段前确认：

1. “按次数排序”中的“次数”是完成次数还是重复次数？
2. 重复任务完成后，是保留历史记录并生成下一次，还是直接移动到下一次日期？
3. 父任务在全部子任务完成后是否自动完成？
4. 分类是否允许用户自定义，还是只保留“生活”和“学习”？
5. 标签是否允许自定义颜色和排序？
6. 拖拽顺序是否只作用于“全部”视图，还是每个视图分别保存顺序？
7. 日历视图需要日、周、月中的哪些粒度？
8. 专注计时器是否需要保存历史记录和统计图表？
9. 深色模式是否需要跟随系统实时切换？
