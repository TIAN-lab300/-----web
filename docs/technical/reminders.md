# 后台提醒与 Web Push 规范

日期：2026-10-02  
状态：待实现  
适用范围：浏览器关闭后仍需触发的任务提醒

## 1. 设计结论

提醒必须尽可能在浏览器页面关闭后继续生效。纯静态、无后端 Web 应用无法满足这一要求，因此采用以下正式架构：

```text
浏览器前端
  -> Service Worker
  -> Web Push 订阅
  -> 最小提醒后端
  -> 提醒调度器
  -> 推送服务
  -> 操作系统通知
```

架构新增服务端，但任务主数据仍保存在浏览器中。提醒后端只保存设备订阅和提醒计划。

## 2. 能力边界

Web Push 可以让通知在页面关闭后到达，但不能在所有设备和浏览器上提供与原生闹钟完全相同的保证。

可能造成提醒延迟或失败的情况：

- 用户拒绝通知权限。
- 用户在系统中关闭浏览器通知。
- 浏览器或操作系统限制后台活动。
- 设备处于省电模式、关机状态或没有网络。
- 浏览器推送服务暂时不可用。
- Service Worker 订阅过期或被撤销。
- 用户清除站点数据，导致本地设备标识和订阅状态丢失。

如果产品要求法律或合同级别的“必定触发”，必须增加原生桌面端或移动端应用，并调用操作系统的本地通知和闹钟 API。

## 3. 组件职责

### 3.1 前端页面

- 管理任务和提醒规则。
- 在用户主动操作时请求通知权限。
- 注册 Service Worker。
- 创建和刷新 PushSubscription。
- 把提醒计划同步到后端。
- 显示提醒权限、同步状态和失败提示。
- 在页面打开时执行前端提醒补偿。

前端不直接发送 Web Push。

### 3.2 Service Worker

负责：

- 接收 `push` 事件。
- 调用 `showNotification()` 显示通知。
- 处理 `notificationclick`，聚焦现有页面或打开应用。
- 处理 `pushsubscriptionchange`，重新订阅并同步后端。

Service Worker 不保存任务主数据，不负责计算重复规则的长期历史。

### 3.3 提醒后端

负责：

- 保存设备订阅。
- 保存提醒计划和重复规则。
- 计算下一次提醒时间。
- 去重和状态管理。
- 调用推送服务发送通知。
- 处理过期订阅和重试。

### 3.4 推送服务

浏览器厂商提供的 Push Service，根据订阅 endpoint 接收 Web Push 消息。

## 4. 设备身份和认证

系统不使用账号，但必须区分设备和授权同步请求。

本地首次启用提醒时：

1. 生成随机 `deviceId`。
2. 生成高熵 `deviceSecret`。
3. 将二者保存在浏览器本地存储。
4. 通过 HTTPS 把 `deviceId` 和一次性提交的 `deviceSecret` 注册到后端。
5. 后续提醒同步使用 `Authorization: Bearer <deviceSecret>`。

约束：

- `deviceSecret` 不得进入 URL。
- 服务端使用 `DEVICE_AUTH_PEPPER` 对 secret 做哈希，只保存哈希，不保存明文。
- 清除浏览器数据后，需要重新注册设备。
- 不使用设备指纹作为身份。

## 5. 订阅流程

```text
用户点击“启用提醒”
  -> 检查 Notification 和安全上下文
  -> 注册 Service Worker
  -> 请求通知权限
  -> 创建 PushSubscription
  -> 注册设备并提交订阅
  -> 获取 VAPID 公钥
  -> 验证后端已保存订阅
  -> 更新界面状态
```

订阅必须由用户主动操作触发。页面加载时不能自动弹出通知权限请求。

## 6. 提醒计划同步

本地任务是提醒计划的来源。提醒发生变化时：

1. 本地任务保存成功。
2. 计算该任务的提醒计划。
3. 验证开始时间、截止时间、重复规则和提醒规则。
4. 生成 `scheduleVersion`。
5. 使用全量替换接口同步当前设备的提醒计划。
6. 后端返回 `acceptedVersion`。
7. 本地记录最近成功同步版本。

建议使用“全量替换”而不是逐条增量修改，减少丢事件和顺序错误：

```text
PUT /api/reminders/schedule
```

请求体包含当前设备全部有效提醒计划。后端在事务中替换旧计划。

离线时：

- 本地保存 `pendingSync` 状态。
- 网络恢复后重新同步。
- 同步成功前不删除本地提醒规则。

## 7. 提醒计划模型

```json
{
  "id": "reminder-id",
  "taskId": "task-id",
  "title": "健身",
  "anchor": "dueAt",
  "fireAt": "2026-10-03T10:00:00.000Z",
  "timeZone": "Asia/Shanghai",
  "recurrence": {
    "mode": "weekly",
    "weekdays": [1, 3, 5]
  },
  "enabled": true,
  "scheduleVersion": 12
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `id` | 提醒唯一标识 |
| `taskId` | 本地任务标识 |
| `title` | 通知标题或任务摘要 |
| `anchor` | 相对开始时间或截止时间 |
| `fireAt` | 下一次需要触发的绝对 UTC 时间 |
| `timeZone` | 用于计算本地重复日期 |
| `recurrence` | 一次性、每天或每周规则 |
| `enabled` | 是否启用 |
| `scheduleVersion` | 防止旧同步覆盖新计划 |

后端不得把提醒计划作为任务主数据返回给前端。

## 8. 重复提醒计算

后端负责计算未来发生时间，因为浏览器关闭时前端无法继续计算。

一次性提醒：

- 只保存一个 `fireAt`。
- 发送成功后状态变为 `sent`。
- 用户编辑后生成新的 `scheduleVersion`。

每天提醒：

- 在目标时区每天同一本地时间触发。
- 夏令时变化时保持本地时钟语义。

每周提醒：

- `weekdays` 使用 `0` 至 `6`，`0` 表示周日。
- 至少选择一个日期。
- 每次发送成功后计算下一次发生时间。

## 9. 发送状态机

```text
scheduled
  -> sending
  -> sent

sending
  -> retry_wait
  -> sending

sending
  -> failed

scheduled
  -> cancelled

scheduled
  -> expired
```

状态说明：

| 状态 | 说明 |
| --- | --- |
| `scheduled` | 等待触发 |
| `sending` | 正在发送 |
| `sent` | 推送服务已接受 |
| `retry_wait` | 暂时失败，等待重试 |
| `failed` | 达到重试上限 |
| `cancelled` | 用户取消或删除 |
| `expired` | 超过允许补发窗口 |

## 10. 重试、去重和幂等

- 同一 `reminderId + fireAt` 只能发送一次通知。
- Service Worker 使用 `tag` 合并重复通知。
- 推送返回 `404` 或 `410` 时，订阅失效，后端删除订阅。
- `5xx` 和网络错误使用指数退避重试。
- 建议重试间隔为 1 分钟、5 分钟、15 分钟。
- 超过补发窗口后不再发送，避免用户收到大量过期提醒。
- 补发窗口默认建议为 15 分钟，最终值需要产品确认。

## 11. 时间和时区

- `fireAt` 使用 UTC ISO 8601 保存。
- `timeZone` 保存 IANA 时区名称。
- 重复规则按本地时区计算。
- 后端和服务端数据库统一保存 UTC 时间。
- 前端显示时转换成本地时区。
- 系统时间变化后，后端以服务器时间为调度基准。

## 12. 通知内容

通知内容有两种模式：

1. 最小隐私模式：只显示“你有一个待办提醒”。
2. 任务摘要模式：显示任务标题和截止时间。

默认建议使用最小隐私模式，并允许用户在设置中开启任务摘要。

通知 payload 不得包含备注全文、标签全集、分类私密信息或其他不必要数据。

## 13. 安全要求

- 必须使用 HTTPS。
- 使用 VAPID 公私钥。
- 私钥只保存在服务端环境变量或密钥管理系统。
- 推送订阅和提醒接口需要设备认证。
- 限制 API 请求频率。
- 校验 payload 大小和字段类型。
- 不允许用户提交任意推送 endpoint 给其他设备。
- 日志中不得输出完整订阅密钥、设备 secret 或任务备注。

## 14. 平台兼容性

至少验证：

- Chrome 桌面版
- Edge 桌面版
- Firefox 桌面版
- Safari 桌面版
- Android Chrome
- iOS 16.4 及以上安装到主屏幕的 PWA

不同平台的权限、后台限制和通知展示方式可能不同，验收记录必须列出操作系统、浏览器版本和安装方式。

## 15. 部署配置

服务端至少需要：

```text
VAPID_PUBLIC_KEY
VAPID_PRIVATE_KEY
VAPID_SUBJECT
REMINDER_TIME_ZONE
DATABASE_URL
ALLOWED_ORIGIN
DEVICE_AUTH_PEPPER
```

前端至少需要：

```text
REMINDER_API_BASE_URL
VAPID_PUBLIC_KEY
```

密钥不得写入前端源码或提交到版本库。

## 16. 测试要求

### 16.1 单元测试

- 一次性、每天和每周提醒时间计算
- 跨月、跨年和闰年
- 夏令时和时区变化
- 去重键生成
- 重试状态转换
- 过期和取消

### 16.2 集成测试

- 设备注册和认证
- PushSubscription 保存
- 提醒计划全量替换
- 调度器选择到期提醒
- 伪推送服务接收消息
- 过期订阅清理

### 16.3 真实浏览器测试

- 用户授权通知
- 页面打开时收到提醒
- 页面关闭但浏览器运行时收到提醒
- 浏览器完全关闭后重新打开时的行为
- 系统通知点击后打开正确任务
- 权限被拒绝
- 设备无网络
- 服务端短暂不可用
- 重复通知去重

“浏览器完全关闭后稳定触发”必须按目标操作系统和浏览器单独验收。Web Push 测试通过不等于原生闹钟级别的绝对保证。

## 17. 完成定义

提醒功能进入生产前必须满足：

- 前端能够主动启用和禁用提醒。
- 后端能够保存、更新和删除提醒计划。
- 重复提醒由后端继续计算。
- 页面关闭后，目标测试平台的提醒可以送达。
- 过期订阅可以自动清理。
- 同一提醒不会重复大量发送。
- 权限、离线、网络失败和服务故障有明确提示。
- 平台限制已经写入用户可见说明。
- 所有关键流程有自动化或可重复的集成测试。
